## 上下文

Create Canvas 当前已经具备：

- 项目级画布快照
- 选中节点上下文
- 服务端 Canvas Agent
- 自动新建 workflow / text / group 的执行链路

但在“已有节点存在时，当前消息到底是继续改旧节点还是新建节点”这个问题上，系统还没有正式协议。

## 目标 / 非目标

- 目标：
  - 让 Agent 在已有节点上下文中显式判断“在原节点上新增”还是“新建节点”
  - 把用户当前 selection 纳入一等输入，而不是仅作为弱参考
  - 把这次判定变成正式结构化输出，供 workflow 和前端共同消费
  - 统一 `auto` 与 `ask` 在节点创建后何时触发 `/generate` 的规则
- 非目标：
  - 不在本次变更里重做全部节点编辑工具
  - 不要求首版支持任意多节点批量复杂编辑

## 决策

- 决策：将“编辑目标判定”放进 supervisor agent 的统一输出，而不是额外引入第二次专门的 agent 调用
  - 原因：当前链路已经收敛到单次 supervisor 决策，继续拆分会增加 LLM 次数和时延

- 决策：当用户意图不明确且已有候选节点时，先走澄清而不是直接猜测
  - 原因：这个分歧是强行为差异，错误代价高于多一次用户确认

- 决策：显式选中的节点优先作为“继续编辑”候选
  - 原因：selection 已经是当前 UI 里最明确的局部上下文信号

- 决策：节点归属判定对 `auto` 与 `ask` 一视同仁
  - 原因：是否沿用原节点属于画布结构决策，不应依赖模式而出现两套不同规则

- 决策：`auto` 与 `ask` 仅在真正触发 `/generate` 的时机上分流
  - 原因：用户对节点归属的确认应先于生成，而 `auto`/`ask` 的差异主要体现在是否还需要场景参数二次确认

## 风险 / 权衡

- 风险：多一次澄清可能增加一步交互
  - 缓解：只在“已有节点存在且用户目标不明确”时触发

- 风险：如果继续编辑能力首版过弱，用户即使选了“继续编辑”也可能感觉结果仍像新建
  - 缓解：在 spec 中明确“在原节点上新增”是沿原节点上下文新增派生节点，而不是覆盖原节点

- 风险：`auto` 模式建完即生成，若节点归属判定有误会放大错误代价
  - 缓解：只有在已有节点且意图不明确时必须先澄清，短提示词仍只返回建议卡片

## 迁移计划

1. 先补 spec 和 supervisor 输出协议
2. 再改 workflow 分支与前端澄清交互
3. 再补 `auto` 与 `ask` 的 `/generate` 触发分流
4. 最后验证短提示词、已有节点、多轮追问和显式 selection 四类场景

## 待决问题

- 当 selection 同时包含 text 节点与 workflow 节点时，哪个优先级更高
