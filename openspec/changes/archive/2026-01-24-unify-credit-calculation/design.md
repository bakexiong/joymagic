# 设计文档：统一前端积分计算

## 上下文

当前项目中，前端组件使用多种方式计算所需积分：

1. **硬编码常量**：如 `const REQUIRED_CREDITS = 6;`
2. **本地计算函数**：如 `getRequiredCredits()`, `calculateRequiredCredits()` 等
3. **分散的逻辑**：每个组件都有自己的计算方式

后端已经提供了统一的 `/api/ai/estimate-credits` 接口，该接口：
- 使用 `credit-config.ts` 和 `pricing-config.ts` 中的配置
- 支持固定积分和动态积分（基于参数）
- 确保计算准确性

## 目标 / 非目标

### 目标
- 统一所有前端组件使用 `/api/ai/estimate-credits` 计算积分
- 确保前后端积分计算一致
- 简化维护，当积分规则变更时只需修改后端配置
- 支持动态积分计算（根据参数实时计算）

### 非目标
- 不改变后端积分计算逻辑
- 不改变积分扣除流程
- 不改变用户界面（仅改变积分获取方式）

## 决策

### 决策 1：创建通用 Hook

**决策**：创建一个 `useEstimateCredits` Hook 来封装积分计算逻辑。

**理由**：
- 统一管理 API 调用逻辑
- 便于实现防抖、缓存等优化
- 便于错误处理和加载状态管理
- 便于在多个组件中复用

**Hook 接口设计**：
```typescript
function useEstimateCredits(apiKey: string, params?: Record<string, any>, options?: {
  enabled?: boolean;
  debounceMs?: number;
}): {
  credits: number | null;
  isLoading: boolean;
  error: string | null;
  refetch: () => void;
}
```

### 决策 2：防抖优化

**决策**：对于动态积分场景，使用防抖（debounce）避免频繁调用 API。

**理由**：
- 用户在输入参数时（如调整视频时长滑块），会频繁触发积分计算
- 防抖可以减少不必要的 API 调用
- 提升用户体验和性能

**防抖时间**：建议 300-500ms

### 决策 3：缓存机制

**决策**：缓存相同参数的积分计算结果。

**理由**：
- 避免重复计算相同参数的积分
- 减少 API 调用次数
- 提升响应速度

**缓存策略**：
- 使用参数组合作为缓存 key
- 缓存时间：建议 5-10 分钟
- 当参数变化时清除旧缓存

### 决策 4：错误处理策略

**决策**：API 调用失败时，显示默认值或错误提示，但不阻止用户操作。

**理由**：
- 积分计算失败不应阻止用户生成内容
- 后端会在实际生成时再次验证积分
- 提供友好的错误提示即可

**错误处理**：
- 网络错误：显示"无法计算积分，请稍后重试"
- API 错误：显示错误信息
- 场景不存在：显示"场景配置错误"

### 决策 5：参数映射

**决策**：前端参数名需要正确映射到后端期望的参数名。

**理由**：
- 前端可能使用驼峰命名（如 `generateAudio`）
- 后端可能期望下划线命名（如 `generate_audio`）
- 需要确保参数正确传递

**映射策略**：
- 在 Hook 中统一处理参数名转换
- 或在前端传递时进行转换
- 确保与后端 `calculateRequiredCredits` 函数的参数格式一致

## 风险 / 权衡

### 风险 1：API 调用延迟

**风险**：每次计算积分都需要调用 API，可能影响用户体验。

**缓解措施**：
- 使用防抖减少调用频率
- 使用缓存避免重复调用
- 显示加载状态，让用户知道正在计算

### 风险 2：网络错误

**风险**：网络不稳定时，积分计算可能失败。

**缓解措施**：
- 实现重试机制
- 显示友好的错误提示
- 允许用户继续操作（后端会再次验证）

### 风险 3：参数格式不一致

**风险**：前端传递的参数格式与后端期望不一致，导致计算错误。

**缓解措施**：
- 统一参数映射逻辑
- 在 Hook 中处理参数转换
- 测试各种参数组合

### 风险 4：性能问题

**风险**：如果防抖和缓存实现不当，可能导致性能问题。

**缓解措施**：
- 合理设置防抖时间
- 合理设置缓存时间
- 监控 API 调用频率
