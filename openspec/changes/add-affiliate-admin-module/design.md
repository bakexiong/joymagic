## 上下文

需求要求参考现有的独立 Affiliate Admin 样式，但确认可以直接集成进当前项目已有的 `admin` 管理后台中。项目已存在 RBAC、admin sidebar、多语言文案和标准后台布局，可复用这些基础设施。

## 目标 / 非目标

- 目标：在现有 admin 中接入一个受权限控制的分销管理模块
- 目标：保证“无权限不可见 + 无权限不可访问”同时成立
- 目标：首版 UI 尽量贴近参考图的信息结构
- 目标：为后续真实数据接入建立可直接落库的分销表结构
- 非目标：本次不实现完整的后端接口与页面数据查询
- 非目标：本次不实现可持久化的审核、配置保存、打款流程

## 决策

- 决策：使用现有 `/admin` 路由体系，新增 `/admin/affiliate/[section]`
  - 原因：复用现有后台布局、面包屑、RBAC、国际化和导航结构，降低维护成本
- 决策：新增 `admin.affiliate.read` 和 `admin.affiliate.write`
  - 原因：先建立模块级能力边界，后续接接口时可继续细分子权限
- 决策：在 sidebar 数据结构中增加 `permission` 字段，并在 server layout 中按权限过滤
  - 原因：确保未授权用户从 UI 层面看不到模块入口，而不仅仅是页面拦截
- 决策：页面使用 mock 数据驱动
  - 原因：当前需求以结构和权限接入为主，先完成前台骨架再接后端更稳妥
- 决策：新增专用分销表，而不是把所有信息塞进 `config` 或 `order` 的零散字段
  - 原因：分销域存在审核、归因、佣金、提现等多阶段状态流，独立表更易维护和审计
- 决策：佣金比例统一使用 `bps`（基点）存储，金额统一使用 `cents`
  - 原因：避免浮点精度问题，并和现有支付金额字段保持一致
- 决策：分销设置使用 `affiliate_program` 独立表保存
  - 原因：配置项具有明确结构和审计需求，优于松散 key-value

## 风险 / 权衡

- mock 数据无法覆盖真实业务边界
  - 缓解：将展示数据集中在共享 block 中，并同步补充分销表结构，后续替换接口时只需接查询层
- 当前只做模块级权限，不区分页面内细粒度操作
  - 缓解：已预留 `admin.affiliate.write`，后续可以继续扩展审核、提现、配置写权限
- 订单和订阅目前尚未直接写入 affiliate 外键
  - 缓解：通过 `affiliate_referral` 和 `affiliate_commission` 先完成业务关联；后续如需优化查询，可再补充冗余外键
