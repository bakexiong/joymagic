## 上下文

当前首页由 `src/app/[locale]/(landing)/page.tsx` 组装 `landing` 翻译数据，再由 `src/themes/default/pages/landing.tsx` 统一渲染。移动端与桌面端共享同一套 Hero 首屏和 Header 结构，首页没有针对移动端的独立信息层级。后台虽已有通用 `config` 表和 `/admin/settings/[tab]` 配置机制，但没有首页模型案例配置。

## 目标 / 非目标

- 目标：
  - 为首页提供移动端独立布局，优先展示 Banner、双 CTA 和模型案例
  - 保留现有 SEO 模块内容，不改文案，只调整移动端顺序与容器布局
  - 让模型案例内容由后台配置驱动，支持后续扩展很多模型
  - 保持移动端菜单展开后沿用现有功能菜单样式与导航结构
  - 为已登录用户提供可回退到旧版首页的明确入口
- 非目标：
  - 不重写桌面端首页
  - 不修改 footer
  - 不新增前端 API key 或任何前端敏感配置
  - 不改动 `/content` 下的任何 MDX 文件

## 决策

- 决策：移动端首页采用与桌面端并行的页面编排，而不是在现有 Hero 内继续堆叠条件分支。
  - 原因：用户要求“移动端布局单独设计，采用独立的布局”。将移动端首页抽成独立编排，可以清晰控制顺序：顶部工具栏 -> Banner slides -> 双 CTA -> 模型案例 -> 原有 SEO 模块。

- 决策：首页现有 SEO 模块继续复用现有 `landing` 数据源与区块组件。
  - 原因：用户明确要求 SEO 文案不做任何修改。复用既有 Hero、Features、FAQ 等区块能降低文案被误改的风险。

- 决策：模型案例配置先落在现有后台 settings/config 体系，使用单个 JSON 配置项存储。
  - 原因：项目已经有通用 `config` 表与后台设置页，适合承载“首页模型案例”这类运营配置，无需引入新表或 CMS 流程。

- 决策：前台读取模型案例配置时必须支持空配置降级。
  - 原因：避免后台尚未配置或配置异常时影响首页整体可访问性；SEO 模块仍应继续渲染。

- 决策：“切换到旧版本”入口放在用户头像下拉菜单中。
  - 原因：用户明确要求该入口位于头像下拉列表内，应遵循该交互约束，同时避免挤占移动端首屏工具栏空间。

## 考虑的替代方案

- 替代方案：直接修改现有 `Hero` 组件，让它同时承载 Banner、双 CTA 和模型案例。
  - 不采用原因：会让 Hero 同时承担桌面端与移动端两套职责，条件分支膨胀，后续维护风险高。

- 替代方案：把模型案例写入多语言翻译文件。
  - 不采用原因：这会把运营配置和 SEO 文案耦合，且不满足“后台可配置”的要求。

- 替代方案：新增专门的后台页面或数据库表。
  - 暂不采用原因：当前需求只要求可配置，现有 settings/config 体系已经足够支撑首版。

## 风险 / 权衡

- 风险：移动端独立布局如果复用不当，可能导致桌面端与移动端内容顺序不一致。
  - 缓解：在规范中明确仅移动端重排，桌面端保持现状。

- 风险：后台 JSON 配置格式过于自由，可能导致渲染异常。
  - 缓解：在规范中要求字段校验、默认值和配置缺失降级。

- 风险：复用现有 Header 逻辑时，移动端顶部操作区可能与当前菜单展开状态冲突。
  - 缓解：在规范中明确汉堡菜单只复用原菜单内容和样式，顶部右侧操作区单独布局。

- 风险：未登录用户没有头像下拉菜单，无法看到旧版入口。
  - 缓解：当前按用户明确要求仅将入口放入头像下拉菜单；实现上保留可配置旧版地址，后续若需要扩展访客入口可单独追加需求。

## 实施说明

- 首版应优先保证结构顺序、配置驱动和回退机制正确，再处理视觉细节。
- Banner slides 与模型案例都应仅影响移动端首页，不改变桌面端已有信息架构。
