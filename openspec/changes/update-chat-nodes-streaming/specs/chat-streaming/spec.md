## 新增需求

### 需求：所有聊天入口必须提供流式反馈

系统必须让所有用户可见聊天入口以流式方式向前端返回执行中的中间反馈，而不是仅在结束后一次性返回最终结果。

#### 场景：标准聊天返回增量文本
- **当** 用户在标准聊天页发送消息
- **那么** 系统必须以流式方式返回 assistant 文本增量
- **并且** 前端必须在最终完成前逐步展示回复内容

#### 场景：Canvas 聊天返回中间推理
- **当** 用户在 Canvas 聊天 Dock 发送消息
- **那么** 系统必须在最终 assistant message 之前流式返回至少一个 thinking / reasoning 事件
- **并且** 前端必须在 thinking 区域实时展示该事件内容

### 需求：Canvas 工作流必须暴露关键步骤的流式事件

系统必须为 Canvas 聊天工作流的关键步骤暴露可消费的流式事件，以支持前端显示推理和进度。

#### 场景：意图规划阶段写出 reasoning
- **当** Canvas 工作流完成意图规划
- **那么** 工作流必须立即写出包含 `reasoning` 的流式事件
- **并且** 该事件不得等待整个工作流结束后才返回

#### 场景：提示词优化阶段写出 reasoning
- **当** Canvas 工作流完成提示词优化
- **那么** 工作流必须立即写出该阶段的 reasoning 或等效中间说明

#### 场景：场景路由阶段写出 reasoning
- **当** Canvas 工作流完成模型/场景路由
- **那么** 工作流必须立即写出该阶段的 reasoning 或等效中间说明

### 需求：流式会话必须保持可恢复的最终状态

系统必须在流式返回完成后仍然保证消息持久化、计费和错误处理状态一致。

#### 场景：流式成功完成后落库
- **当** 一次聊天流式执行成功结束
- **那么** 系统必须写入最终 assistant message
- **并且** 历史消息中不得出现重复 assistant 记录

#### 场景：流式执行失败后返回错误
- **当** 聊天流在执行过程中失败
- **那么** 系统必须向前端返回可见错误状态
- **并且** 失败后的计费与退款逻辑必须保持一致
