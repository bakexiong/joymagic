## 新增需求

### 需求：Create Canvas 必须提供基于 Mastra 的服务端智能体平台

系统必须为 `/{locale}/create/canvas/[projectId]` 提供基于 Mastra 的服务端智能体平台，用于承载聊天式创作、结构化画布操作和生成编排，不得继续将智能体主逻辑长期保留在前端页面组件内部。

#### 场景：前端提交智能体消息

- **当** 用户在 Create Canvas 中发送一条聊天消息
- **那么** 前端必须调用服务端智能体接口
- **并且** 服务端必须负责意图理解、工具调用和结构化结果生成

#### 场景：前端保持画布交互

- **当** 用户执行节点拖拽、缩放、平移或局部 UI 操作
- **那么** 这些低延迟交互仍可由前端本地处理
- **并且** 不得要求每个画布手势都往返服务端

### 需求：系统必须区分 Agent 推理层与 Workflow 执行层

系统必须将开放式聊天理解交给 Mastra Agents，将确定步骤的状态更新与生成执行交给 Mastra Workflows，不得把两者混为单一黑盒调用。

#### 场景：用户提出开放式创作需求

- **当** 用户提出一个步骤并不明确的创作目标
- **那么** Agent 层必须负责生成结构化计划
- **并且** Workflow 层必须负责按顺序执行该计划

#### 场景：系统落地图状态

- **当** 智能体决定创建节点、更新节点或创建连线
- **那么** 这些变更必须通过 Workflow 调用正式工具与服务层完成
- **并且** 不得直接把未经校验的模型输出当作最终持久化结果

### 需求：系统必须采用 Supervisor Agent 协调子 Agent

系统必须使用一个 supervisor agent 协调至少一个或多个专用子 Agent，以分离创作意图解析、场景路由、prompt 优化和结果解释等职责。

#### 场景：系统处理复杂创作需求

- **当** 单条聊天消息同时包含媒体类型判断、参考图理解和生成策略选择
- **那么** supervisor agent 必须能够按需委派给专用子 Agent
- **并且** 最终返回统一的结构化计划与用户可读回复

### 需求：系统必须支持基于 Skill 的场景化智能体能力

系统必须支持基于 Mastra Workspace Skills 的 `skills` 能力，用于承载场景化创作策略、工具白名单、工作流骨架和回复风格，而不是只将其作为前端静态展示卡片。

#### 场景：Workspace 暴露 skills

- **当** 系统初始化 Canvas Agent 运行时
- **那么** 必须通过 Mastra Workspace 配置 skills 目录
- **并且** Agent 必须能够通过官方 skills 能力发现、读取和搜索 skill 内容

#### 场景：第一期仅接入 skill 能力底座

- **当** 团队以最小范围接入 skills
- **那么** 系统只需要先支持 Workspace Skills 的目录接入、发现、读取和搜索能力
- **并且** 不要求第一期同时交付任何正式业务 skill 内容

#### 场景：用户显式选择 skill

- **当** 用户在 Canvas Agent 面板中选择一个 skill
- **那么** 服务端必须基于该 skill 缩小可用工具、提示词和工作流骨架范围
- **并且** 后续自动生成的画布节点必须遵循该 skill 的默认结构和布局策略

#### 场景：系统自动识别 skill

- **当** 用户未显式选择 skill 但消息中包含明确场景信号
- **那么** supervisor agent 或 scene-router-agent 必须能够推断最匹配的 skill
- **并且** 响应中必须保留最终使用的 skill 标识，供前端展示和后续追问复用

说明：该场景属于后续扩展能力，第一期可先不启用自动 skill 判定。

#### 场景：不同 skill 绑定不同节点骨架

- **当** 系统针对不同创作场景自动搭建画布
- **那么** 不同 skill 必须能够绑定不同的节点模板、引用关系和默认布局
- **并且** 不得让所有 skill 共用单一且不可配置的通用工作流结构

#### 场景：skill 正文与 UI 元数据分离

- **当** 系统为前端展示 skill 卡片
- **那么** 前端可以读取轻量元数据用于图标、标题和描述
- **并且** Agent 实际消费的技能说明必须来自 Workspace 中的 `SKILL.md` 与参考资料，而不是仅依赖前端传回的描述文本

### 需求：系统必须将现有画布与生成能力封装为 Mastra Tools

系统必须将项目读取、画布图读取、节点写入、连线写入、生成触发、上传、模板和历史资产能力封装为 Mastra tools，而不是让 Agent 直接耦合数据库查询或前端组件状态。

#### 场景：Agent 需要读取项目上下文

- **当** Agent 需要知道当前项目、节点或引用资源
- **那么** 它必须通过正式工具读取这些信息
- **并且** 工具返回结果必须具备稳定 schema

#### 场景：Agent 需要触发生成

- **当** Agent 决定发起图片或视频生成
- **那么** 它必须通过正式生成工具调用现有生成链路
- **并且** 不得新增绕开现有生成接口的专属协议

#### 场景：Agent 需要解析 `@参考图`

- **当** 用户在聊天消息中通过 `@` 引用某张参考图
- **那么** 系统必须通过正式工具解析该引用对应的画布节点、历史素材或上传资产
- **并且** 不得要求前端直接拼接最终的引用关系结果

### 需求：系统必须支持自动生成画布节点

系统必须支持根据聊天消息、当前 selection、引用素材和已选 skill 自动生成正式画布节点，而不是仅返回文本建议。

#### 场景：用户请求新建工作流

- **当** 用户提出一个新的图片或视频创作任务
- **那么** 系统必须能够自动创建对应的 workflow 节点、必要的 input 节点和连接边
- **并且** 这些节点必须以正式快照形式回写到当前项目

#### 场景：系统批量落图

- **当** 一条消息需要同时创建多个节点和多条边
- **那么** 系统必须使用结构化操作批量完成节点、连线和布局写入
- **并且** 不得依赖前端逐条拼装节点关系

#### 场景：系统自动布局

- **当** 智能体新建了一组节点
- **那么** 系统必须自动为其应用稳定布局策略
- **并且** 不得要求模型直接输出不可控的最终像素坐标

### 需求：系统必须支持上传图片并在聊天中引用参考图

系统必须支持用户在 Canvas Agent 聊天中上传图片，并通过正文中的 `@参考图` 机制引用已上传图片、画布图片节点或历史素材。

#### 场景：用户上传图片作为聊天参考

- **当** 用户在发送消息前上传一张图片
- **那么** 系统必须能够将该图片作为 attachment 传入服务端智能体链路
- **并且** 后续工作流必须能够把该图片映射为正式参考输入

#### 场景：用户通过 `@` 明确引用参考图

- **当** 用户在消息中输入 `@参考图` 或选择某个可引用素材
- **那么** 系统必须将该引用解析为明确的 reference target
- **并且** 解析结果必须可用于自动创建 reference edge 或注入 workflow reference 参数

#### 场景：聊天记录保留上传与引用上下文

- **当** 系统保存一条聊天消息
- **那么** 该记录必须保存关联的上传资产 ids、引用目标 ids 或等价摘要
- **并且** 页面恢复时必须能够还原该消息使用过哪些参考图

### 需求：系统必须为 Canvas Agent 提供项目级 Memory

系统必须为 Canvas Agent 提供围绕 `projectId` 的会话记忆，以保存消息历史、用户偏好和项目目标，但不得让 memory 替代画布项目快照作为图状态真相源。

#### 场景：用户在同一项目中连续多轮对话

- **当** 用户在同一 Canvas 项目中进行多轮追问
- **那么** Agent 必须能够记住前文目标、限制和偏好
- **并且** 这些上下文必须通过 memory 层获得

#### 场景：系统读取画布图状态

- **当** Agent 需要了解当前节点、边和布局
- **那么** 它必须从项目快照或正式图模型服务读取
- **并且** 不得仅依赖 memory 中的自然语言摘要来还原画布

### 需求：系统必须持久化保存聊天记录，并与 Canvas Project 关联

系统必须将 Canvas Agent 的聊天记录作为正式业务数据持久化保存，并与对应的 `projectId` 建立强关联，而不能只依赖 memory 或前端本地缓存。

#### 场景：保存项目级聊天消息

- **当** 用户在某个 Canvas Project 中发送消息或收到 assistant 回复
- **那么** 系统必须保存该条消息及其关联的 `projectId`、`threadId` 和角色信息
- **并且** 该记录必须能够用于后续页面恢复和审计

#### 场景：按 project 恢复聊天记录

- **当** 用户重新进入 `/{locale}/create/canvas/[projectId]`
- **那么** 系统必须能够根据 `projectId` 读取该项目下的最近会话和消息列表
- **并且** 不得要求前端依赖仅存在于浏览器内存中的临时状态

#### 场景：memory 不替代正式聊天记录

- **当** 系统同时使用 Mastra memory 和项目级聊天记录
- **那么** memory 可以用于上下文压缩、召回和偏好保存
- **并且** 正式消息展示、历史恢复和计费审计必须依赖持久化聊天记录

### 需求：系统必须支持 Editor 版本化管理智能体配置

系统必须接入 Mastra Editor，用于管理 code-defined agent 的指令、prompt blocks 和工具描述的可编辑覆盖版本。

#### 场景：非开发角色调优智能体

- **当** 产品、运营或提示词工程师需要调整智能体行为
- **那么** 他们必须能够通过 Editor 修改允许覆盖的配置
- **并且** 不得要求每次微调都修改代码并重新部署

#### 场景：系统发布智能体版本

- **当** 团队准备将一版智能体配置投入生产
- **那么** 系统必须支持 draft、published 和 archived 等版本状态
- **并且** 生产请求默认必须使用 published 版本或显式指定版本

### 需求：系统必须通过专用 Canvas Agent API 对外暴露能力

系统必须为 Create Canvas 暴露专用的智能体服务端 API，用于创建会话、发送消息、获取线程历史和返回结构化画布操作。

#### 场景：前端发起一条消息

- **当** 前端向 Canvas Agent API 发送消息
- **那么** 响应中必须包含用户可读回复以及结构化画布操作或任务状态
- **并且** 前端必须能够据此更新本地图和继续监听生成结果

#### 场景：安全边界

- **当** 前端调用 Canvas Agent API
- **那么** 所有模型调用、工具调用和第三方密钥都必须留在服务端
- **并且** 前端不得持有任何新增敏感 key
